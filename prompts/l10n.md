# Localization Migration: `Localizations` → `L` + `Localizable.xcstrings`

## Goal

Replace Conjugar's legacy localization approach with the one used by its sibling apps
**Conjuguer** (`/Users/josh/Desktop/workspace/Conjuguer`) and **Konjugieren**
(`/Users/josh/Desktop/workspace/Konjugieren`):

- A type-safe `enum L` with scoped accessors backed by `String(localized:)`.
- A single `Localizable.xcstrings` string catalog holding **both** English (base) and
  Spanish, replacing the current `NSLocalizedString` calls + the UTF-16
  `es.lproj/Localizable.strings`.

Reference implementation to imitate:
- `Konjugieren/Konjugieren/Utils/L.swift` — the `L` enum shape.
- `Konjugieren/Konjugieren/Assets/Localizable.xcstrings` — catalog structure.
- **`Konjugieren/CLAUDE.md`, "Localization" section** — the hard-won editing tips.

`String(localized:)` and `.xcstrings` need iOS 16 / Xcode 15+. Conjugar targets iOS 17+,
so this is fine.

## Current state (what you're migrating FROM)

English base strings are **split across two Swift files** — both must feed the catalog:

- `Conjugar/Supporting/Localizations.swift` — 70 `NSLocalizedString` calls. Most use the
  **English text as the key** (e.g. `NSLocalizedString("Start", comment: "")`); a few use a
  **symbolic key + `value:`** (e.g. `bothMasculineText`, `purposeAndUseText`).
- `Conjugar/Models/Info.swift` — 28 `NSLocalizedString` calls. This is where the **long
  rich-text Info/tense bodies** keep their English `value:` (e.g.
  `NSLocalizedString("purposeAndUseText", value: """^Purpose^ …""")`,
  `presenteDeIndicativoText`, `futuroDeIndicativoText`, `pretéritoText`, etc.). The
  headings come from `Localizations.Info.*`.

Spanish lives in `Conjugar/es.lproj/Localizable.strings` — **UTF-16**, keyed by a mix of
English text (`"Start" = "Comenzar";`) and symbolic keys (`"purposeAndUseText" = "…";`).
There is **no `en.lproj`**; English is implicit today (the key or the `value:` param).

Call sites: ~79 `Localizations.*` references across ~26 files.

There is also `Conjugar/es.lproj/LaunchScreen.strings` — **out of scope**, leave it alone.

## Escaping & newline differences (READ THIS — the main foot-gun)

`.strings` and `.xcstrings` have **different escaping and newline rules**. Getting this
wrong silently corrupts the catalog or mangles the rich text.

**`.strings` (old, UTF-16, C-style):**
- Values are `"…"` with interior quotes as `\"`.
- **Literal newlines are allowed** inside a value — Conjugar's rich-text blocks are
  physically multi-line in the file.
- File is UTF-16; a naive UTF-8 read produces garbage.

**`.xcstrings` (new, JSON, UTF-8):**
- Values are JSON strings: interior `"` **must** be `\"`, backslash **must** be `\\`.
- **Literal newlines are NOT permitted** — every newline must become `\n`. So each
  rich-text block collapses to **one physical JSON line** with `\n` escapes. (This is also
  why Grep is useless inside `.xcstrings` — see tips below.)

**Do not hand-translate escaping.** Use real parsers so escaping/newlines convert
automatically:
- Read the Spanish `.strings` with a plist/strings parser rather than by hand, e.g.
  `plutil -convert json -o - Conjugar/es.lproj/Localizable.strings` → a clean
  `{oldKey: spanishValue}` JSON dict (handles UTF-16, quotes, and newlines for you).
- Build the `.xcstrings` by emitting JSON with a real serializer (`json.dump` /
  `JSONSerialization`), never by string-concatenating values. The serializer produces
  correct `\"` and `\n` automatically.

**Percent signs — distinguish two kinds:**
- App **markup** like `%terminology%`, `%voseo%`, `%presente de indicativo%` is the rich-text
  parser's tappable-term syntax, NOT printf. It is (and stays) a **single** `%`. These keys
  are looked up with no format arguments, so the `%` is passed through literally — do **not**
  double them.
- Actual **format specifiers** (`%d`, `%@`) are the ones that need care — see pluralization
  and positional specifiers below.

Other markup (`^Heading^`, `~italic~`, `$RED$`, `$voY$`) is literal text; no escaping in
either format.

## Plan

### 1. Design `enum L` with scoped keys

Rename `Localizations` → `L`, rename the file `Localizations.swift` → `L.swift`, and drop the
stale `// genstrings -o es.lproj *.swift` comment. (Confirm `L` doesn't already collide with a
type in the project.) Keep Konjugieren's conventions:

- One accessor per key: `static var start: String { String(localized: "Quiz.start") }`.
- Scoped keys `Feature.purpose`: `Quiz.start`, `Settings.region`, `Info.purposeAndUseText`,
  `Verb.irregular`, `Model.numberAndPercent`, etc. Feel free to reorganize the enum
  hierarchy for clarity (the current split into `BrowseInfo`, `Quiz`, `Settings`, `Info`,
  `Model`, `ModelSort`, `VerbSort`, `Verb`, `Results` is a good starting point; the loose
  top-level strings like `bothMasculine`, `spain`, `easy`, `gameCenterFailure` should get a
  home).
- Functions for parameterized strings: `static func multipleRatings(count: Int) -> String {
  String(localized: "…\(count)") }` (see pluralization).

### 2. Consolidate ALL English base strings into the catalog

English is currently implicit. In the catalog it must be **explicit** under `"en"`. Pull the
English text from:
- `Localizations.swift` — the key itself, or the `value:` param when symbolic.
- `Info.swift` — the `value:` param of each long body.

Every `Info.swift` `NSLocalizedString` should also be routed through `L` (add
`L.Info.purposeAndUseText`, `L.Info.presenteDeIndicativoText`, …) so no raw
`NSLocalizedString` remains anywhere.

### 3. Build `Localizable.xcstrings` (both languages, no lost translations)

This is the highest-risk step: the Spanish rich-text prose is hours of translation and must
not be dropped. Recommended workflow — **script it, produce a reviewable mapping**:

1. Enumerate every string as a row: `newScopedKey`, `englishText`, `oldStringsKey`.
   `oldStringsKey` is how it appears in `es.lproj/Localizable.strings` (English text for
   most, symbolic for the big ones).
2. Extract Spanish: `plutil -convert json -o - Conjugar/es.lproj/Localizable.strings`.
3. For each row, assemble a catalog entry with `en` = englishText and `es` = the matched
   Spanish, both `"state": "translated"` (so Xcode won't treat Spanish as stale and fall
   back to English). `sourceLanguage` = `"en"`.
4. Emit the file with a JSON serializer. Then **validate**:
   `python3 -c "import json; json.load(open('Conjugar/.../Localizable.xcstrings'))"`.
5. Confirm every old key was consumed — log any `.strings` key with no mapping (missing
   translation) and any new key with no Spanish. No silent drops.

### 4. Proper pluralization

Use xcstrings plural **variations** (`variations.plural` with `one`/`other`, `%lld`) instead
of separate hard-coded singular/plural strings. Two sites:

- **`Model.verbsUsing`** — currently `verbUsing` ("One verb uses this model") +
  `verbsUsing` ("%d verbs use this model"). Collapse into **one** pluralized key:
  `one` → "One verb uses this model", `other` → "%lld verbs use this model". Clean case
  (a model always has ≥1 verb; no zero).
- **Ratings** — currently `noRating` / `oneRating` / `multipleRatings(%d)`. Collapse
  `oneRating` + `multipleRatings` into **one** pluralized key (`one` → "There is one
  rating…", `other` → "There are %lld ratings…"). **Keep `noRating` a separate string** and
  select it at the call site when `count == 0`. Rationale: English and Spanish CLDR plural
  rules map **0 → `other`**, so a plural "zero" category would never be chosen for count 0 —
  the distinct "No one has rated…" sentence must be picked by the caller, not the plural
  engine. (This mirrors Konjugieren's `RatingsFetcher.noRating` / `oneRating` /
  `multipleRatings(count:)`.)

Provide plural variations for **both** `en` and `es`.

### 5. Positional format specifiers + `%lld`

For multi-argument strings, use positional specifiers so translators can reorder:
`Model.numberAndPercent` "Model %@ · %d%% irregular" → `Model %1$@ · %2$lld%% irregular`.
Prefer `%lld` over `%d` for `Int` (what Xcode's catalog generates). Single-arg strings need
no positional index.

### 6. Migrate call sites

Update the ~79 `Localizations.*` references across ~26 files to `L.*`. Mostly mechanical, but
the Info/tense rich-text is where a bad key mapping shows up **visually**, so those deserve
extra care.

### 7. Xcode project registration

- Add `Localizable.xcstrings` to the Conjugar target in `project.pbxproj`.
- **Remove** the `es.lproj/Localizable.strings` reference from `project.pbxproj` and delete
  the file (its content now lives in the catalog). Leave `LaunchScreen.strings`.

### 8. Document the hard-won tips in `CLAUDE.md`

Add a "Localization" section to **Conjugar's `CLAUDE.md`** (not README.md), porting the tips
from Konjugieren's `CLAUDE.md`, adapted to Conjugar's paths:

- **The Edit tool corrupts `.xcstrings`.** Edit operates on *rendered* text, so JSON's `\"`
  displays as a plain `"`; any edit that adds/removes/changes an ASCII `"` (U+0022) inside a
  value writes an **unescaped** quote and breaks the catalog. Rule: edit `.xcstrings` values
  containing ASCII quotes via `python3` on the raw file, not Edit. Unicode curly quotes
  `" " „` need no escaping and are safe with Edit.
- **Always validate after editing:**
  `python3 -c "import json; json.load(open('…/Localizable.xcstrings'))"`.
- **Grep is useless inside `.xcstrings`** — each value is one very long JSON line, so matches
  truncate to `[Omitted long matching line]`. To find a phrase: Grep for the line number,
  then Read at that offset. To replace: Python with a unique nearby word as an anchor to hit
  the correct language section.
- **The `.strings` vs `.xcstrings` escaping/newline differences** from the section above
  (literal newlines legal in `.strings`, must be `\n` in `.xcstrings`; UTF-16 vs UTF-8; the
  markup-`%` vs format-`%` distinction).

### 9. Verify

- `swiftlint`.
- Build: `xcodebuild -project Conjugar.xcodeproj -scheme Conjugar -destination 'platform=iOS
  Simulator,name=iPhone 17' build`.
- Tests: the full suite with `-parallel-testing-enabled NO`.
- JSON-validate the catalog (step 3).
- **Run the app in the simulator in BOTH languages** (use the `run-in-simulator` skill) and
  spot-check the Info tab's rich-text screens in English and Spanish — that's where a
  mis-mapped key or a botched newline conversion is visible.

Per project convention, add a `docs/blog_notes.md` entry summarizing the migration.
